# 個人化貓咪生成系統：持續工作原則

本文件為 2026-09-30 訂定的專案工作原則，適用每次實驗與每個階段。

## 每次行動前先判斷

1. **目的**：這個行動推進哪項原需求？須同時維持照片身份、cat.png 美術方向、約 3500 三角面與後續動畫相容性；不得為了方便驗證而縮小需求。
2. **自動化**：玩家換一隻貓後，系統能否自行取得所需輸入、執行、檢查並處理失敗？仍需哪些人工判斷、點位、遮罩、座標或提示詞調整？
3. **適用範圍**：這是通用處理、一次設定的美術規格、可由個體資料自動推導的參數，還是只適用本例的修補？把手工常數寫進程式只能重播本例。
4. **個案必要性**：若為個案，是否為驗證全系統一致性調整所必要？共通問題與假說是什麼？能否轉成相同規則，自動依不同貓調整？純粹把一張展示圖修漂亮，且沒有通用價值的操作，不持續投入。
5. **證據與停止條件**：如何比較前後效果、辨識錯誤及驗證其他貓？本例成功不代表新貓可用。先界定有限嘗試與採用／拒絕條件，避免無限重生、局部手修或堆疊修復步驟。

以上是行動前的決策，不是事後補一句「未自動化」。同一目的的連續唯讀檢查可共用判斷；更換方法、資料、目標或增加成本前，重新判斷。

## 如何選擇行動

- 優先改進能移除逐貓人工、提升共通品質或建立可靠驗收的環節；能省略的處理不預設成必經步驟。
- 必要的個案 POC 可以做，但須能回答共通問題，明列人工依賴、泛化路徑和停止條件；不得宣稱整套系統已自動化。
- 固定風格設定、每貓自動推導參數、每貓人工修補分開記錄。自動推導失敗時可拒絕、要求針對性補拍或進入已定義審查，不靜默猜測並放行。
- 不用新增這隻貓專屬的標點、座標、遮罩或程式分支來冒充通用進步；確有必要時依上述個案條件處理。
- 幾何、花色、眼睛、材質與動畫分別驗收。面數達標、API 成功、腳本可執行、單視角好看，都不是最終品質通過。
- 拓樸或姿勢改動後重建受影響的表面對應、骨架／權重與驗收；2D 花色點不當作 3D 關節。

## 紀錄與回報

- 新的重要實驗在執行前寫入目的、適用範圍、自動化方式、人工依賴、個案必要性及驗證／停止條件；沿用 experiments 下的紀錄，不另起大量文件。
- 使用 `action_gate` 保留上述簡短判斷。舊實驗只能標為回溯評估，不得偽稱曾完成行動前檢查。
- 每次回報說清楚移除了哪項人工、在哪些輸入實測、尚未驗證什麼；不捏造自動化率或未知人工耗時。
- 實驗證據見 `experiments/generation-v001/experiment-history.json`；問題與泛化限制見同目錄 `automation-review.json`。

## 保持既有邊界

- `readme.md` 不加入實驗內容；測試獨立放在 `experiments/`，流程總覽使用 `workflow.md`。
- 已購原始資產與 `<catworld>` 唯讀，不為測試修改。
- AI 參考圖、真實照片、3D 實際渲染清楚區分；保存輸入、參數、版本、失敗與輸出，不以示意圖冒充模型。
